# Tutorial Studio architecture

Tutorial Studio records editor meaning rather than relying on browser input replay. Mouse and pointer cues are presentation data layered over the same semantic timeline.

## Module boundaries

| Layer | Responsibility | May depend on TurboWarp internals? |
|---|---|---|
| `journal/` | Complete snapshots, transactions, schema and persistence ports | No |
| `replay/` | Direction, ordering and executable block-action contracts | No |
| `bridge/` | Scratch Blocks, VM, browser and storage adapters | Yes |
| future UI | Timeline editing and playback controls | Only through Studio contracts |

Scratch Blocks event groups define adjacent events that form one user action. Events without a group stay separate. Transactions never cross target IDs, so undo and replay can select the correct sprite before applying an edit. All events inside a transaction replay without presentation delays; tutorial pacing occurs only between transactions. A block's internal create-then-position sequence therefore remains exact without exposing its temporary position as a separate tutorial step.

Project operations which have no Blockly event—currently sprite lifecycle and supported costume, backdrop and sound addition/share/lifecycle/reorder operations—store exact before/after restore points. The capture boundary copies editing-target IDs and name/stage references before invoking the VM method; it never retains a mutable target object across an in-place rename. History therefore restores the complete project and then selects the editing target appropriate to that boundary without depending on a deleted or renamed runtime identity. If an operation leaves the semantic structural hash unchanged, its temporary checkpoint is removed and no empty transaction is recorded.

Direct monitor writes do not emit Scratch Blocks events. The small GUI utility seam instead opens a semantic edit around the existing assignment. A scalar range opens one gesture on mouse/touch/key interaction and commits its final value on release, key-up, blur or teardown, so all intermediate input frames remain one visible step. A normal list blur, add, remove or import stores one minimal splice; the two synchronous writes produced by Enter share a short-lived gesture group. Both transaction types retain the sprite being edited for camera/history navigation while their data delta independently identifies the actual global or local data owner. Cloud scalar values deliberately bypass this local replay seam.

Sprite-info controls also bypass Blockly. Studio wraps the VM's existing `postSpriteInfo` boundary and stores
changed target properties in the same versioned data-delta contract as variables and lists. A submitted field
or visibility/rotation control becomes one visible transaction. While the VM exposes a stage drag target,
repeated pointer-move updates retain one initial property snapshot and commit only when `stopDrag` runs, so a
continuous drag is one `Move sprite` step rather than a stream of x/y frames. Replay validates the expected
property value before using the target's ordinary setters; layer changes are ordered after other properties.

Scratch Blocks emits field-change events while each character is typed into its inline HTML editor. The capture bridge buffers only that active editor's changes and commits one snapshot when it closes or loses focus, retaining the first old value and final new value. One-click fields such as dropdowns remain immediate, and an edit that returns to its original value is discarded. This normalization happens before journaling, so all later layers retain the ordinary field-change contract.

Captured target references contain the runtime ID plus the sprite name and stage flag. Replay prefers the ID in the current runtime, then resolves the equivalent target after a checkpoint restore by stage or name. This survives the runtime IDs changing when an `.sb3` is loaded. Renaming, deleting and recreating targets will need explicit timeline events before this becomes a permanent identity scheme.

Block IDs can also be regenerated by checkpoint serialization, especially for embedded shadow literals. New event snapshots add an optional durable block reference: the root block's type and rounded workspace coordinate, followed by named input or next-block steps. Replay keeps the recorded ID as a fast path and uses the semantic reference only when that ID is absent. The resolved current workspace child is then mapped to the VM, keeping both representations synchronized after reload. Duplicate indistinguishable roots at the same coordinate are rejected by falling back to strict validation rather than guessing.

Replay always produces a forward-running action. A backward block creation becomes a deletion; a backward deletion becomes a creation using captured XML; field values and move locations are swapped. List `var_create`, `var_delete` and `var_rename` events are inverted in the same way. Their compact definition record retains owner, value and monitor metadata so recreating a deleted list restores the visible reporter without relying on Scratch Blocks' transient undo stack.

Top-level move coordinates retain the exact finite coordinate delivered by Scratch Blocks. `Blockly.Events.Move.toJson()` rounds its text form, but scratch-vm receives the original floating-point `Coordinate`; near a half-pixel boundary those two values can serialize to different project coordinates. Studio therefore uses the exact semantic snapshot for replay and reserves rounded coordinates for fuzzy durable block-reference lookup only. Existing integer-coordinate journals remain valid.

## Studio history commands

An active Studio session owns user-requested block undo and redo through a transaction cursor over the persisted journal. The cursor is project-wide. When the next transaction belongs to another sprite, the first command selects that sprite and frames its editing view without moving the cursor; repeating the command applies the transaction. Same-sprite commands apply immediately. Recording at an earlier cursor truncates the abandoned redo suffix before appending the replacement transaction.

The bridge intercepts only user command surfaces: Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z, Ctrl/Cmd+Y and Scratch Blocks' workspace context-menu Undo/Redo items. Keyboard requests are serialized: a burst finishes the active presentation, applies intervening verified transactions without animation and animates the terminal request. It deliberately does not replace `workspace.undo()`, because Scratch Blocks uses that method internally while correcting invalid drags and procedures. Detaching the Studio session restores the original context-menu functions and removes the keyboard listener; normal TurboWarp remains unchanged when the query-flagged session is absent.

Move-only semantic fallback detaches the complete affected set and reconnects recorded destinations parent-first. This matches Scratch Blocks' complete-group move filtering and avoids transient descendant cycles when undoing a middle-stack rearrangement. Generic mixed transactions, including grouped create-plus-move, resolve both old and new parents through their durable parent references before applying the Blockly event or mirroring it to the VM; restored checkpoint IDs must never leak into either topology. A native rearrangement whose recorded next block heals onto the dragged block's old parent performs that same `unplug(true)` healing under Undo isolation before starting the genuine single-block drag. A semantic inverse rearrangement presents the dominant moved block and its complete value/statement-input subtree through a 150 ms proxy pinned to its live ID. Only blocks connected through the moved block's next connection are excluded, so reporters and shadows travel with their owning block while the neighbouring command stack settles independently. Fast lifecycle motion is connection-aware (below for append, right for insertion, diagonal for nested input) and carries the visible red pointer by default; `studio-history-pointer=0` disables only that pointer presentation. Native Undo/Redo uses seven motion frames plus one marker-hold frame, closely matching the semantic duration, while full panel Play keeps the realistic 24-plus-12 timing.

`Play` at a partial cursor continues with the remaining transactions. `Play` at the recorded head first rewinds so it can still act as a complete tutorial replay command. Rewind applies only the transaction prefix represented by the cursor.

Realistic Play owns one target-resolved pointer controller for the full sequence. Interaction drivers
describe lazy semantic targets rather than cached coordinates; the controller resolves the current DOM
bounds immediately before movement, then hands endpoint-exact points to a swappable path model. The
default `natural` model uses bounded distance/target-size timing and a slight curve, while
`studio-pointer-model=deterministic` selects the fixed generated model. Once pickup starts, the native
driver's shared clock remains authoritative for both pointer and Blockly coordinates. Ordinary history
sets pointer travel off and retains its faster presentation policy.

Pointer targeting uses the centre of a compact stemless north-west-facing pointer head rather than the
operating-system cursor-tip convention. The overlay keeps that semantic target fixed while the black/white
artwork leans into movement, then decays through a momentum-seeded rocking motion around its own centre
above a red underglow and tight contact shadow. A shared click beat pauses briefly at the resolved target,
compresses the inner shape without cancelling that rotation, activates the real control, then springs back
during a short post-click pause.
These presentation frames run on the same interruptible interaction clock; changing the pointer path model
does not change target resolution or click coordinates. Native drags use the same press/release artwork
without inserting extra geometry frames.

An exact one-event dropdown field change uses a dedicated realistic-Play driver. It resolves the live
block and field semantically, opens `FieldDropdown` through the normal Scratch Blocks field gesture, then
targets the rendered menu item by language-neutral option value. The pointer travels to both current DOM
targets and the option receives the same hover/down/up/click sequence as Closure's menu action contract.
Verification waits for the real field event and requires matching workspace and VM values without changing
the Studio journal or native Undo/Redo stacks. Ordinary history continues to apply the same event
semantically and does not open UI.

Broadcast-message creation is a two-event transaction even though Scratch closes the dropdown event group
before its asynchronous prompt callback: a `broadcast_msg` variable create followed by the selecting
`BROADCAST_OPTION` field change. Capture records the definition immediately and the journal coalesces this
pair; load-time normalization also repairs the historical deferred order. Broadcast definitions remain
structural project state rather than authored scalar/list values. Realistic forward Play opens the existing
field menu, selects Scratch Blocks' language-neutral New Message option, types through GUI-004 and confirms
with the recorded ID. Semantic replay dependency-orders variable definitions before block XML which refers
to them, and removes definitions only after dependent blocks. Verification requires the actual prompt,
paced final text, matching Blockly field ID, matching VM field name plus ID, stage definition and unchanged
Studio/native histories. Ordinary Undo/Redo remains fast and silent.

A forward custom-block definition create-plus-move transaction can use the real My Blocks dialogue. The
driver parses the recorded prototype mutation into ordered label, text/number and Boolean parts, selects the
registered Make a Block flyout callback, then uses the existing Add Input, Add Boolean, Add Label, warp,
Cancel and OK controls through language-neutral `data-studio-target` attributes. Every Blockly editor is
typed at five frames per character. Scoped ID-generator wrappers supply the recorded argument ID while an
input is added and, after the OK callback's event-group request, the recorded definition, prototype and
argument-reporter IDs. Verification requires the observed create and move, matching prototype mutation,
workspace and VM IDs, final coordinate, typed-value evidence, visible dialogue, and unchanged Studio/native
Undo histories. Failed or cancelled playback invokes the real Cancel action so the editor is never left
behind a modal.

Built-in sprite creation, costume/backdrop addition and sound addition are project-operation transactions because they do not emit
Blockly events. Realistic forward Play first presents the actual GUI journey: it resolves the sprite card,
editor tab, library button and exact library asset by language-neutral attributes, moves the shared pointer
between their live bounds, and clicks the existing React handlers. It awaits the real asynchronous VM method
before verification for supported sprite/costume/backdrop interactions, then restores the recorded after-checkpoint
so generated IDs and complete asset state remain exact. Sound operations currently use the same exact
checkpoint contract but deliberately report semantic-only presentation until a verified sound-library and
editor driver exists. Rewind and ordinary history retain checkpoint-only mutation. The structural hash excludes the
redundant `md5ext` asset field in `structural-v3`, because Scratch may omit it for a new library costume and
reconstruct it on checkpoint load while `assetId` plus `dataFormat` remain unchanged.

## Replay viewport

Viewport position is optional presentation state on a transaction, separate from its Scratch events and project hashes. New recordings store the visible workspace origin in scale-independent workspace coordinates. After every internal event in the transaction completes, replay restores that origin using the current workspace scale and dimensions.

Older journals without viewport data preserve the outgoing view when the edited block is already fully visible. Otherwise, deterministic stack framing places the root block 64 pixels from the top-left, moving it up or left only as far as needed to reveal the focal edit. Before applying the transaction, the bridge retains this root-and-focus frame so Undo or Delete can use the meaningful authored location after removing the block.

Both policies produce one scroll target through the viewport bridge. A Scratch-independent motion controller eases to that target over 180-450 ms according to travel distance and suppresses movement of at most 2 pixels. The transaction captures its outgoing visible origin before target selection, so Scratch restoring another sprite's cached workspace does not create an intermediate jump. An editable camera track can later replace the target or timing policy without changing recording or replay semantics.

Before an offscreen create action, the viewport bridge can move to the transaction's authored view before revealing the block. It resolves the intended anchor from the transaction's final move, its destination parent or the serialized create XML, in that order. The policy is an injected `wait`, `concurrent` or `off` mode; `wait` is the default. The chosen target is retained as a scale-independent workspace origin. After creation, the bridge converts that origin through Scratch Blocks' new content bounds and synchronously re-anchors it, avoiding insertion jitter or a second visible camera correction.

## Persistence and checkpoints

The journal serializer is versioned and browser-independent. `journal-store.js` accepts the Web Storage interface today and can be replaced without changing recording or replay code. The browser spike stores one journal per `studio-take` query value. Transaction viewport data is optional, so existing version-1 journals remain valid and use deterministic framing.

Full project checkpoints reuse TurboWarp's existing restore-point database, which stores project JSON and deduplicated assets in IndexedDB. Studio's checkpoint port keeps that implementation behind a narrow contract. The only upstream change makes `createRestorePoint` resolve its generated ID, allowing the journal to reference the exact base checkpoint.

The project-state port derives separate structural and authored projections from canonicalized `vm.toJSON()` output. Structural state retains blocks, sprite and data definitions, assets, monitor definitions/layout and project configuration, while excluding variable/list contents, monitor values and persisted target properties that running scripts can change. New takes label this hash `structural-v5`: it includes the v3 redundant-`md5ext` normalization, v4 canonical block references and v5 canonical Scratch VM tuple input references. Explicit older structural versions retain their exact projections for saved checkpoint compatibility, and version-1 journals without a label continue using their original full-project hashes. `Set Base` starts a take on the preferred contract. A rewind must match the take's recorded base hash, and playback also matches the recorded end hash when one is available.

The authored-state bridge holds the last boundary values for non-cloud variables and lists, plus deliberately adopted persisted target properties such as position, direction, visibility, costume and layer order. VM execution signals mark that shadow dirty without instrumenting individual data primitives or compiler output. At the next visible block transaction, or before leaving the recorded head through Undo or Rewind, Studio compares dirty data with the shadow and appends the delta to the preceding visible transaction. Scalars store before/after values; lists store one prefix/suffix-minimized splice. Forward replay applies optional before-data, block events and optional after-data; backward replay reverses that order. Runtime-boundary deltas remain hidden, while deliberate scalar-slider and list-monitor edits use the same delta representation as visible steps. Applying either kind refreshes visible Scratch monitors immediately.

If only data changed, same-sprite Undo seals that data and applies the transaction in one command. Runtime changes to target properties still use the conservative preparation command: stop execution, remove clones, restore and verify the authored shadow, then frame the transaction without moving the cursor. Cross-sprite commands likewise retain the first-command navigation stage. Full Rewind performs preparation within its single explicit operation.

`Set Base` deliberately adopts the current live values and creates a new checkpoint. Generic `PROJECT_CHANGED` events do not copy all data because block edits would make that an expensive hot path. Future semantic data and property actions will update the authored shadow directly. Cloud values are excluded from capture and restoration so replay cannot cause network writes.

List history currently persists the changed middle as a single splice, avoiding a copy of an unchanged tail after insertion or deletion. List definition history stores only that one list and its monitor, not a project snapshot. A future adaptive payload port can move large arbitrary rewrites into content-addressed chunks without changing the transaction contract.

`Set Base` creates a checkpoint from the current project and starts a clean journal. It is useful for bounded experiments and for declaring a new take after a non-block edit. It is not a substitute for semantic data/property events or target lifecycle events: those operations still need explicit contracts before they can be edited on the timeline.

An external `PROJECT_LOADED` event, including File → New, is a hard compatibility boundary. Studio-owned checkpoint restores are explicitly scoped and ignored by this detector. Any other project replacement pauses capture, preserves the journal and checkpoint, and disables playback controls with a reload instruction; it never tries to apply the old take to the new project.

## Failure policy

Malformed serialized journals fail at the parse boundary. Capture errors are contained so authoring continues. Replay errors stop at the failing action, mark the playback position unknown and release the UI from its busy state. Undo records and validates the end hash when it first leaves the recorded head; redo validates that hash when it returns.

When the canonical head is available in the current session, a hash mismatch also reports the first differing JSON path and compact values. This keeps strict validation actionable without storing another complete project snapshot in the journal.

The final Undo and full Rewind share one canonical-base validator. If event-by-event reversal leaves an internal Scratch state difference, the session restores its canonical base checkpoint and validates again. Redo remains available only when that repair produces the exact recorded hash; an unrepaired base mismatch still marks the position unknown and prevents forward playback. This keeps the checkpoint authoritative without weakening validation or adding special cases to individual block events.
